# Дорожня карта продукту

Статус: **запропоновано — очікує затвердження власником** · Дата: 2026-11-20
Пов'язані: [mvp-scope.md](mvp-scope.md) · [product-feature-map.md](product-feature-map.md) · [product-metrics.md](product-metrics.md) · [monetization-strategy.md](monetization-strategy.md) · [development-process.md](development-process.md)

Етапи визначаються **бізнес-результатом**, який вони дають. Етап завершується, коли виконано критерії виходу, а не коли побудовано його екрани. На задачі реалізації розбивається лише поточний затверджений етап (див. [development-process.md](development-process.md)); пізніші етапи лишаються на рівні продуктового планування і будуть переглянуті з реальними даними.

Цільові значення з позначкою **[Г]** — робочі гіпотези, які треба підтвердити на Етапі 0; це не галузеві орієнтири.

```mermaid
flowchart LR
  S0["Етап 0<br/>Визначення і перевірка"] --> S1["Етап 1<br/>Базовий MVP"]
  S1 --> S2["Етап 2<br/>Утримання"]
  S2 --> S3["Етап 3<br/>Монетизація"]
  S3 --> S4["Етап 4<br/>Зростання"]
  S4 --> S5["Етап 5<br/>Оптимізація і розширення"]
```

### Перша віха розробки — **M1.1 «Базовий цикл логування»**
Найтонший наскрізний зріз, що перевіряє найризиковішу залежність (дані про продукти) і основну цінність:
- CT-01 «Сьогодні» (фіксована тимчасова норма, прийоми, кільце без станів коридору), CT-02 з пошуком + «Нещодавнім», CT-03 шторка порції, CT-04 редагування / видалення, «Готово» → оновлений CT-01.
- Реальна інтеграція бази продуктів; локальне збереження; події аналітики для воронки логування.
- **Готово, коли:** внутрішні тестувальники записують повний день реальної їжі; пошук знаходить не менше погодженого покриття за тестовим списком Етапу 0; повторний запис — 3 натискання; події воронки видно в аналітиці.
Наступні віхи (деталізуються лише після M1.1): M1.2 онбординг + розрахунок норми + безпека / режим без норми; M1.3 швидке додавання, доопрацювання сесії з кількома продуктами, офлайн, минулі дні, стани коридору; M1.4 налаштування, згода, штрихкод (якщо входить), закрита бета.

## Етап 2 — Утримання

| | |
|---|---|
| **Бізнес-мета** | Підвищити утримання від першого тижня до першого місяця, щоб була база, яку варто монетизувати |
| **Мета користувача** | Бачити, чи я в плані цього тижня; легко повертатися; бачити зміну ваги |
| **Функції** | F-20 Прогрес · тиждень + деталі дня + пояснення + панель вкладок; F-21 рядок тижня на «Сьогодні»; F-22 нейтральні тексти дня і банер повернення; F-24 облік ваги і тренд; F-25 нагадування; повернення порад про зважування на ON-09; F-15 дописування з Прогресу · Could: F-26 повтор прийому, F-23 перевірка «малого» дня (якщо SD-04 = Етап 2), F-34 необов'язковий акаунт |
| **Перевикористані екрани** | PR-01, PR-03, PR-04, панель вкладок, стани CT-01 зі сторінки 02, потік дописування |
| **Нові екрани** | Введення ваги і тренд; згода на нагадування і їх налаштування; (необов'язково) вхід в акаунт |
| **Відкладено** | PR-02 місяць, AI, пейвол |
| **Залежності** | Правила повного дня (`calculation-specification.md`) реалізовано й перевірено за `calculation_reference.py`; ≥ 1 тиждень даних користувачів |
| **Метрики успіху** | Утримання D7 / D30, щотижнево активні, перегляди Прогресу на щотижнево активного, розуміння «повних днів» (тест), частка згод на нагадування |
| **Критерії виходу** | Утримання логування D30 покращено відносно бази Етапу 1 на погоджену величину [Г: +5 п. п.] · тест розуміння Прогресу пройдено (люди можуть пояснити, чому день не рахується) · вагу записують ≥ 30 % щотижнево активних користувачів, які худнуть [Г] |

## Етап 3 — Монетизація

| | |
|---|---|
| **Бізнес-мета** | Почати регулярний дохід, не зашкодивши утриманню |
| **Мета користувача** | Платити за те, що економить час або дає глибше розуміння; базовий облік лишається безкоштовним |
| **Функції** | F-29 пейвол, плани, пробний період; F-30 керування підпискою і відновлення; F-28 фото / AI (Premium, з безкоштовною спробою [Г]); F-27 місяць і довша історія (кандидат у Premium) — див. [monetization-strategy.md](monetization-strategy.md) |
| **Перевикористані екрани** | CT-05, CT-06 + стани; іконка камери CT-02 і «Додати через фото / AI»; PR-02 |
| **Нові екрани** | Пейвол / порівняння планів; статус підписки в налаштуваннях; пропозиції оновлення в точках входу |
| **Відкладено** | Голосове логування (без підтвердження), адаптивна норма |
| **Залежності** | Білінг магазину; AI-постачальник із відомою вартістю розпізнавання; рішення щодо ціни |
| **Метрики успіху** | Конверсія з безкоштовного в платний, з пробного в платний, MRR, відтік, AI-розпізнавань на Premium-користувача, утримання D30 безкоштовних (не має падати) |
| **Критерії виходу** | Конверсію і MRR виміряно щонайменше за один платіжний цикл · валова маржа на Premium-користувача додатна з урахуванням витрат на AI · утримання D30 безкоштовних не нижче бази Етапу 2 |

## Етап 5 — Оптимізація і розширення

| | |
|---|---|
| **Бізнес-мета** | Покращити утримання й економіку; додати підтверджені сценарії |
| **Мета користувача** | Норма, що підлаштовується під мене; менше ручного введення |
| **Функції** | F-32 адаптивна норма (концепція готова; вирішити A-Q3…A-Q5); F-23 перевірка «малого» дня, якщо відкладено; F-33 цілі Б/В/Ж; F-35 інтеграція з Health; голосове логування — лише після підтвердження |
| **Перевикористані екрани** | Прогрес, патерн пояснення ON-09 |
| **Нові екрани** | Повідомлення про зміну норми; дозволи Health |
| **Залежності** | ≥ 14 днів записів + вага для користувачів двигуна; правила якості даних |
| **Метрики успіху** | Утримання користувачів двигуна проти контролю, відтік, ARPU, прийняття змін норми |
| **Критерії виходу** | Визначаються для кожної ініціативи |
